## DEF-01　內文含惡意 HTML 時會執行腳本（儲存型 XSS 風險）　✅ 已修正
- **嚴重度**：高
- **重現**：開啟新聞 `9900001`（固定資料裡構造的新聞，內文含 `<img src=x onerror=alert(1)>`）。
- **預期**：腳本不執行，內文被清理或以文字顯示。
- **實際（修正前）**：跳出 `alert(1)`，腳本被執行。
- **根因**：`app.js` 的 `renderArticlePanel` 以 `${content}` 把 `article.content` 直接放進 `innerHTML`。程式註解說明這是為了渲染爬蟲留下的 `<p>`、`<!--N-->`，但同時也讓內文成為腳本注入的入口：只要上游新聞來源或爬蟲被竄改，每個開啟該篇的使用者都會執行。爬蟲只移除 `script`、`style` 等標籤，不處理 `onerror` 這類事件屬性，不能當作防線。
- **影響範圍**：所有新聞詳情面板；內文來自外部網站，不受本專案控制。
- **修正**：前端新增 `sanitizeHtml()`，以 DOMPurify 3.4.17（`vendor/purify.min.js`，sha512 已與 cdnjs 官方值比對）依白名單清理後再插入。白名單依 157 篇真實新聞內文用到的標籤制定（排版、表格、圖片加圖說、連結）。
- **驗證**：攻擊測試轉為通過；157 篇真實內文清理後文字內容皆無變動，被移除的只有 1 個 `iframe`、1 個 `input`、1 個 `label`。DOMPurify 未載入時退回純文字顯示，不會原樣插入。

## DEF-10　單篇摘要與類別摘要的寫入點同樣會執行腳本　✅ 已修正
- **嚴重度**：高
- **重現**：攔截請求讓摘要 API 回傳含 `<img src=x onerror=alert('xss')>` 的內容，再打開單篇摘要或類別摘要。
- **實際（修正前）**：兩處都執行了腳本。類別摘要的寫入點原本沒有任何測試，是盤點所有 `innerHTML` 時發現的。
- **根因**：`generateArticleSummary`（`${result.summary}`）與 `renderCategorySummaryResult`（`body.innerHTML = summary`）直接插入。摘要由 LLM 依外部新聞產生，內容不受控制；後端格式化（`advanced_format_summary`、`get_formatted_summary`）也不跳脫。
- **修正**：同 DEF-01，兩處都經過 `sanitizeHtml()`；後端的跳脫仍是 DEF-02，屬第二道防線。
- **驗證**：兩個攻擊測試轉為通過；另有回歸測試確認摘要的編號清單、類別摘要的標題與段落排版沒有被破壞。

## DEF-11　用輸入法打中文時，每個字都送出搜尋（含組字中的注音）　✅ 已修正
- **嚴重度**：低（影響體驗與後端請求量）
- **重現**：用注音輸入法在搜尋框打「味全龍」。
- **預期**：停下來之後才搜尋，組字中的注音符號不會被搜尋。
- **實際（修正前）**：3 個字送出 6 次請求，包括 `ㄨㄟˋ`、`味ㄑㄩㄢˊ` 這類組字中的暫時內容；查不到結果時畫面會閃出「找不到符合搜尋條件的新聞」。
- **根因**：
  1. `onSearchInput` 監聽 `input` 事件，輸入法組字過程中這個事件照樣觸發，沒有排除組字狀態。
  2. 防抖只有 350ms，打中文時字與字之間要按好幾個鍵再選字，停頓很容易超過，每個字都被當成「已經停下來」。
- **為什麼原本的防抖測試沒抓到**：那個測試用英文字母快速連打，驗證的是防抖機制本身；Playwright 輸入中文會一次插入整串字，不會觸發組字事件，所以測不到真實的中文輸入。
- **修正**：`app.js` 的 `onSearchInput` 在 `e.isComposing` 為真時直接略過，並新增 `compositionend` 監聽，組字結束時再搜尋；防抖時間抽成常數 `SEARCH_DEBOUNCE_MS` 並放寬到 500ms。
- **驗證**：新增用 CDP `Input.imeSetComposition`／`Input.insertText` 模擬注音輸入的測試：組字中停頓超過防抖時間也不送請求，選字確認後各送一次（`味`、`味全`）。拿掉 `isComposing` 判斷後該測試失敗（組字中送出 `ㄨㄟˋ`）。

## DEF-12　單篇摘要偶爾回 500：輸出被思考用掉而截斷　✅ 已修正
- **嚴重度**：中（偶發，但使用者點擊「生成 AI 摘要」直接看到錯誤）
- **重現**：點擊沒有摘要的新聞的「生成 AI 摘要」，偶爾回 500；不是每次都發生。
- **預期**：正常產生摘要；真的失敗時給使用者看得懂的訊息。
- **實際（修正前）**：web 容器紀錄有 `JSONDecodeError`（兩次，位置都在輸出的第 106 到 112 個字元，分別是「字串沒有結尾」與「逗號後面期待下一個欄位」，是 JSON 被攔腰截斷的典型錯誤）。
- **根因**：`gemini/client.py` 的單篇摘要 `max_output_tokens = 2048`。Gemini 的思考 token 也算在這個上限裡（官方文件），長文章的思考就能用掉 1700 多，剩下的空間寫不完 JSON。實測 6 篇較長的文章：思考 546 到 1732 token、實際輸出 220 到 350 token，其中一篇合計 2013，離上限只剩 35 個 token。後端又沒有檢查回應是否正常結束，直接把截斷的文字交給 `json.loads`。
- **限制**：失敗當時的原始輸出沒有被記錄，所以「被截斷」是由失敗位置與餘裕推論，不是直接重現。
- **修正**：
  1. 單篇摘要的 `max_output_tokens` 提高到 8192。
  2. 單篇摘要的思考程度降為 `low`（批次與類別摘要維持預設，類別摘要需要跨篇推理）。
  3. `generate_summary` 檢查 `finish_reason`，不是正常結束或內容為空就丟 `GeminiResponseError` 並記錄原因；JSON 解析失敗也包成同一個例外並記錄原始回應（截短）。
  4. 單篇摘要失敗時自動重試一次。
  5. Web API 對仍然失敗的情況回 502「摘要暫時產生失敗，請稍後再試」，LINE 回覆同樣訊息（原本 LINE 沒有任何回應）。
- **思考程度比較**（4 篇已有摘要的新聞，同一份內容各生成一次，未寫入資料庫）：

  | | 預設 | low |
  |---|---|---|
  | 思考 token | 643 到 1504（平均約 1179） | 0 |
  | 計費的輸出 token（思考加輸出，4 篇合計） | 5922 | 1198（約少 80%） |
  | 耗時（平均） | 約 13.3 秒 | 約 4.6 秒 |
  | 摘要中的數字在原文找不到的個數 | 0 | 0 |

  兩者的數字都有原文出處。預設版的味全龍那篇出現原文沒有的「家樂福」（舊的資料庫摘要也有），low 版沒有；樣本只有 4 篇，不能據此說預設版比較容易出錯。
- **驗證**：單元測試 12 個（設定、截斷、空回應、重試、502、LINE 回覆）；真實 Gemini 呼叫走完整路徑確認新設定可用且正常結束。

## DEF-02　後端摘要未跳脫 HTML
- **嚴重度**：中（前端已能擋住腳本執行，剩下是顯示不正確與缺少第二道防線）
- **重現**：開啟新聞 `9900002`（已存摘要含 `<b>`、`<script>`），點「生成 AI 摘要」。
- **預期**：特殊字元以文字顯示。
- **實際**：`<b>粗體標籤</b>` 被渲染成粗體；API 回傳的摘要裡 `<script>` 與 `&`、`<` 原樣存在。
- **根因**：後端 `gemini/formatting.py` 沒有任何跳脫。前端無法分辨摘要裡的標籤是後端排版用的，還是 LLM 文字裡的字面內容，所以這件事只有後端能正確處理。
- **建議**：後端在組成 HTML 前先對文字內容跳脫，再套上自己的排版標籤。

## DEF-05　不存在的新聞要求摘要回 500　✅ 已修正
- **嚴重度**：中
- **重現**：`POST /api/news/0000000/summary`（帶正確金鑰）。
- **預期**：404，與詳情端點一致。
- **實際**：500。
- **根因**：`gemini/locking.py` 的 `generate_summary_with_lock` 查不到新聞時仍執行 `query_result[0]`，空結果造成例外。
- **影響**：使用者傳入無效 ID 會看到「伺服器發生錯誤」，且過程中已取得 Redis 鎖與呼叫流程。
- **建議**：查詢結果為空時直接回 404，不要進入生成流程。
- **修正**：`gemini/locking.py` 查不到新聞時丟 `NewsNotFoundError`（不再取 `query_result[0]`，也不呼叫 Gemini）；Web API 轉成 404（訊息「找不到這則新聞，可能已過期，請重新整理頁面」）；LINE 回覆「這則新聞已過期，請重新選擇類別查看最新新聞」。
- **補充**：每天 00:00 會清空資料，網頁開著過夜或 LINE 聊天記錄裡的舊按鈕都會遇到這個情況，所以實際發生的機率比表面上高。LINE 原本會因為例外被吞掉而完全沒有回應。
- **驗證**：E2E、單元測試各有對應測試（含 LINE 回覆、Gemini 不被呼叫）。原本的單元測試 `test_get_news_summary_not_found` 假設「找不到時回 200 加空摘要」，與真實行為不符，已改成預期 404。

## DEF-04　搜尋關鍵字只能完全相等　✅ 已修正
- **嚴重度**：中
- **重現**：搜尋「寧德」（新聞 `9836834` 的關鍵字是「寧德時代」，標題不含「寧德」）。
- **預期**：找到該新聞，搜尋框提示是「搜尋標題或關鍵字」。
- **實際**：找不到；搜尋完整的「寧德時代」才找得到（有正向測試）。
- **根因**：`infrastructure/repositories/news_repository.py` 的 `web_search_news` 用 `%s = ANY(keywords)`，是完全相等比對。
- **建議**：要支援部分比對，可改用 `EXISTS (SELECT 1 FROM unnest(keywords) k WHERE k ILIKE ...)`；或把提示文字改成「搜尋標題」。
- **修正**：搜尋範圍改為「標題、內文、關鍵字」任一個含有搜尋字串（不分大小寫、部分比對）。內文是爬蟲留下的 HTML，比對前先用 `regexp_replace` 去掉標籤與註解，否則搜尋 `p`、`img`、`href` 或 `!--` 會比對到標籤而列出不相關的新聞（有測試）。前端提示文字改為「搜尋標題、內文或關鍵字」。
- **範圍**：只改網頁搜尋（`web_search_news`）。LINE 的關鍵字查詢是另一段程式，仍然只比對標題與完全相等的關鍵字，沒有改。

## DEF-03　搜尋 `%`、`_` 被當成萬用字元　✅ 已修正
- **嚴重度**：低
- **重現**：搜尋 `%`。
- **預期**：只列出標題真的含 `%` 的新聞（固定資料有 1 篇）。
- **實際**：列出全部 14 篇。
- **根因**：`web_search_news` 把使用者輸入包成 `f"%{keyword}%"`，沒有跳脫 `%` 與 `_`。不是 SQL 注入（參數化查詢，另有測試確認），但搜尋結果不正確。
- **建議**：先把使用者輸入中的 `\`、`%`、`_` 跳脫，再包 `%`。
- **修正**：新增 `escape_like()`，把輸入裡的 `\`、`%`、`_` 加上反斜線再包成 `%…%`；網頁搜尋與 LINE 關鍵字查詢都套用。
- **驗證**：單元測試覆蓋跳脫函式；E2E 搜尋 `%` 只回傳真的含 `%` 的 3 篇（預期結果依固定資料動態計算），搜尋 `_` 回 0 筆。

## DEF-06　超長無空白標題超出卡片　✅ 已修正

- **重現**：列表中新聞 `9900003`（標題是一長串無空白英文）。

- **修正**：`styles.css` 的 `.card-title` 加上 `overflow-wrap: anywhere`。對應測試轉為通過。

## DEF-07　「尚無摘要」被快取　✅ 已修正
- **嚴重度**：低
- **重現**：選「兩岸」→ 按「生成分類摘要」看到「尚無摘要」→ 關閉；之後後端產生該類別摘要 → 同一頁面再按一次。

- 標題的特殊字元在卡片與詳情標題都以文字顯示（前端對標題有做跳脫）。
- 內文的 `<p>`、`<!--N-->` 被渲染成段落，不會以字面顯示；長內文可在面板內捲動。
- 分類篩選、搜尋、空狀態、關閉面板（✕／Esc／點遮罩）、摘要生成失敗後可重試、403／503／連線中斷時的橫幅。
